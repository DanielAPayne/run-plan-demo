# Run-plan demo

Most automations are built, handed over, and then break quietly. This repository shows the other way to do it: one small automation that is **run** the way a client's should be. It is watched, tested every day, alerted on failure, and reported from its own records.

**What is real and what is not.** The leads are synthetic: a simulator sends invented people with `.test` addresses, and the "email service" is a local inbox. Everything about how the system runs is real and measured: every run, reply time, test, failure and fix.

**How it was built.** An AI coding agent (Claude Code) built and ran this demo under my direction, including the drill and the fix described below. Directing agents and holding their work to evidence is how I work.

## What it does

A lead comes in from a web form. The automation saves it, replies within seconds, and follows up after 1, 3, 7 and 14 days until the lead books or opts out.

## What makes it a run plan

| Promise to the client | How it is kept here |
|---|---|
| **Nothing is lost** | The lead is saved before anything else happens. If the reply can't be sent, a retry picks it up every 5 minutes |
| **Watched** | Every run is recorded by n8n; every lead has a row in the run log |
| **Alerted** | Any failed run records an incident and sends an alert. Repeats of the same failure are counted, not re-alerted |
| **Tested** | Once a day a marked test record goes through the real front door. It must be saved, replied to within two minutes, and its email must really arrive |
| **Still caught if the tool itself dies** | A watchdog outside n8n checks n8n's health, the 5-minute heartbeat, and that a daily test passed in the last 26 hours |
| **Alerts survive the outage they report** | Alerts go through a separate channel from the email service |
| **Reported** | `scripts/report.py` writes the report from the database. No figure is typed by hand |

## What happened so far

**The drill, 2026-11-11.** The email service was stopped and a lead was sent. The timeline is in [reports/DRILL_2026-11-11.md](reports/DRILL_2026-11-11.md):
- the form still got its answer and the lead was saved;
- the incident was recorded 0.1 seconds after the lead arrived, and the alert was in the alert channel 0.2 seconds after;
- two retries failed while the service was down, and were counted on one incident with no second alert;
- 2 seconds after the service came back, the retry sent the reply. The lead got exactly one email, 4 minutes 38 seconds after arriving.

**A real fault, found on the first morning.** The watchdog had sent about 1,466 false "RESOLVED" alerts overnight, one a minute for each of its three checks. It read a database status line as a result. Nothing was missed, but an alert channel full of noise hides real alerts. It is fixed, recorded as an incident, and shown in the report. A review of the alert channel found it.

**The first report** is [reports/REPORT_2026-11-11.md](reports/REPORT_2026-11-11.md). It covers only the first hours, so it has one lead. It fills in as the simulator runs.

## The parts

Five containers, listening on the local machine only:

| Container | Role | For a client this would be |
|---|---|---|
| `n8n` (2.47.3) | Runs the seven workflows | Their n8n, Make or Zapier |
| `postgres` (17.11) | The leads, messages, tests, incidents and heartbeats; also n8n's own records | Their CRM plus a small log table |
| `mailpit` | Stands in for the email service; keeps every message | Their email provider |
| `alertbox` | The alert channel, kept separate on purpose | Slack, SMS or a second provider |
| `watchdog` | Checks from outside n8n, every minute | An external dead-man's-switch service |

Seven workflows, generated by [workflows/build.py](workflows/build.py) so that every node can be reviewed in one file:

1. New lead: save, reply, start follow-ups
2. Retry: reply to any lead that is still waiting
3. Follow-ups: days 1, 3, 7 and 14
4. Daily test: one marked record through the whole flow
5. Heartbeat: every 5 minutes
6. On any failure: record an incident, then alert
7. Demo only: a synthetic lead every two hours, 08:17 to 20:17

## Run it yourself

You need Docker and Python 3.

```sh
python3 scripts/make_env.py   # writes random local passwords to .env (never committed)
sh scripts/setup.sh           # starts the containers, imports and publishes the workflows
```

| To | Do |
|---|---|
| See the workflows | http://localhost:5678 (the login is in `.env`) |
| See the emails it sent | http://localhost:8025 |
| See the alerts | http://localhost:8026 |
| Write a report | `python3 scripts/report.py` (add `--days 30` for a month) |
| Send a lead by hand | `curl -X POST http://localhost:5678/webhook/lead -H 'Content-Type: application/json' -d '{"name":"A Person","email":"a.person@example.test","service":"roof repair"}'` |
| Run the daily test now | `curl -X POST http://localhost:5678/webhook/ops/daily-test` |
| Close an incident | `sh scripts/resolve.sh <id> "<what fixed it>"` |
| Re-apply after changing a workflow | `sh scripts/setup.sh` |
| Stop it / start it | `docker compose stop` / `docker compose start` |

## Limits, stated plainly

- **No language model.** The reply is chosen by rule in the "Draft reply" node. A client build puts a model there, with the client's key; everything around it stays the same.
- **It runs on a laptop.** When the laptop sleeps, the demo sleeps, and the heartbeat shows the gap. A client's system runs on a server, with the watchdog elsewhere.
- **The watchdog shares the host.** Here it is a container beside n8n, so it can't report the whole machine being down. For a client it is an outside service.
- **A reply can be sent twice in one rare case:** the email goes out, and the step that records it fails. The retry then sends again. A client build records the intent to send first.
- **The "run now" doors have no password.** They are reachable only from the local machine. For a client each needs a secret.
- **Bookings and opt-outs are not simulated,** so every synthetic lead gets all four follow-ups.
- **One person, no on-call rota.** Alerts are only useful if someone reads them; the false-alert fault above sat for a night.
